- 検索だけを実行して見つかったページと、その本文で確認できたこと：
  - `uv run python -m app.retrieval "LoRA QLoRA 違い"` の上位5件は，第2回 p.52 → p.51 → p.60 → p.47 → p.61
  - 答えの根拠になるのは p.52（「元の重みは固定し，小さな『差分』だけを学習する（LoRA）．さらに元の重みを 4bit に圧縮する（QLoRA）」）と，補足の p.51（PEFT の一覧での LoRA・QLoRA の説明）
  - p.60・p.61（演習の進め方），p.47（知識の追加は RAG が効きやすい）は，「QLoRA」「LoRA」という語が出てくるだけで，質問の答えにはならない．似た用語のページと根拠のページは別だと確認できた
- `--trace`で見えたツール呼び出し（ツール名・引数・回数、Treeでたどった目次など）：
  - ベクトル検索：`search_materials({'query': 'LoRA 固定 学習 QLoRA 加える'})` を1回．モデルが質問から検索語を組み立てている
  - Graph：`search_graph({'query': 'LoRA QLoRA 固定 学習'})` を1回

- 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例：
  - 全文投入は，入力上限のエラーにはならず，p.52 の本文も入力に含まれていた．それでも答えを書かず，ヒントだけを返した．全文投入の指示文の「宿題の答えそのものは書かず，考え方のヒントで導く」を，講義内容の質問にまで当てはめたと考えられる．根拠は入力されていたのに，回答に使えなかった例

- 今回の用途に採用したい方式と、その理由・比較条件の限界：
  - 1ページで答えがそろう質問なら，ベクトル検索を採用したい．全文投入の約 1/39 の入力トークンで，費用も最も安く，回答も正しかった．Graph も速く正しいが，入力は約2倍になる．Tree は正しく探せたが，時間が5倍以上かかった
  - 限界：質問は1つ，各方式1回だけの実行で，同じ質問でも結果は揺れる．全文投入だけ対象資料が9資料と広い．全文投入の失敗は取得方法ではなく指示文の影響なので，方式の優劣とは分けて考える必要がある
- 気づき・疑問：

  - 検索の距離が近いページでも，答えがあるとは限らない（p.60・p.61・p.47）．引用ページを自分で開いて確かめる必要がある

- やったこと（変更したファイル・設定・処理、または設計した取得方法）：
  - `app/retrieval.py` に `add_neighbors()` と `search_with_neighbors()` を追加し，ベクトル検索で当たった各ページに，前後1ページの本文を付けて返すようにした
    - `load_pages()` のページ一覧から資料ごとのページ順を作り，検索結果と同じ `document_id` の中だけで前後を探す（別の資料はまたがない．資料の先頭・末尾では片側だけ）
    - 同じページは1回だけ返す．前後ページが別の検索結果と重なったときは，検索結果として扱い，距離を残す
    - 当たったページごとに「前のページ → 当たったページ → 次のページ」の資料の順に並べる．前後ページには `role: "前後ページ"` と `neighbor_of`（どの検索結果の前後か）を付ける
  - `app/config.py` に `RAG_NEIGHBOR_WINDOW`（環境変数 `AIE_RAG_NEIGHBORS`，既定 0）を追加し，`app/tools.py` の `search_materials` から使うようにした．`AIE_RAG_NEIGHBORS=1` を付けたときだけ前後ページが付き，付けなければ元の検索と同じ結果になる．ツールの docstring は変えていないので，同じコマンドで変更の前後を比べられる
  - `python -m app.retrieval --neighbors 1 "検索語"` で，検索だけの結果を前後ページ付きで確認できるようにした
  - `tests/test_neighbors.py` を追加した（APIを呼ばない5件．window=0 で元のまま，資料の順に並ぶ，資料をまたがない，重複しない，検索結果と重なったページは距離を残す）．`uv run pytest -q` は 26 passed

  - 前後ページを足しても，モデルは引用ページを変えなかった．モデルは渡された中から根拠になるページを選べていて，増えたページに引きずられて回答が崩れることもなかった
